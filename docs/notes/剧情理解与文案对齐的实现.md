# 剧情理解、文案写作、音画对齐：实现机制拆解

对照代码：`aicutplan 0.10.0`；对照产物：EP01（170 窗 / 14 块 / 54 句 / 1057 字）。
一行结论：**它不「看懂整部片」，而是把片切成事件 → 聚成块 → 按块预算选镜 → 对着窗口写句 → 用契约和 TTS 适配把句子钉死在窗口上。**

---

## 〇、六个中间产物，一条链

```
源片
 └─① asr_ja.json / ja-segments.json       台词源（内嵌字幕优先，ASR 兜底）
     └─② story_plan.events[]               事件（8–14 个/180s 段，带 t0/t1/type）
         └─③ story_plan.blocks[]           剧情块（12–15 块，六段式，带 t0/t1/target）
             └─④ cutplan.windows[]         窗口（每块按事件权重领镜，0.8–3.5s/窗）
                 └─⑤ window_table.md       写作输入表（按块分组，逐窗给画面/台词/预算）
                     └─⑥ narration.json + align.json   句子（ws/we/src → t0/dur）
                         └─ out/03-*.mp4             TTS 适配进槽位 → 混音 → 合片
```

每一步都能单独查、单独改、单独校验——这是「可审计」的来源，也是事故能定位的原因。

### 实际执行顺序（`cf_pipeline.py:120-223`）

| # | 步骤 | 谁在算 | 产物 | 可跳 |
|---|---|---|---|---|
| 0 | 污染检查 | 算法 | 告警 | — |
| 1 | 台词源预检（有内嵌字幕就替换 ASR） | 算法 / ASR 模型 | `ja-segments.json` | `--subs no` |
| 2 | 因果图谱 | **LLM（文本）** | `story_plan.causal` | `--skip-plan` |
| 3 | 画面先定（选窗 + 钩子） | **纯算法** | `json/cutplan.json` | `--skip-plan` |
| 4 | 无声粗剪 | ffmpeg（工程脚本 `cut.py`） | `out/02-video-rapid-silent.mp4` | `--skip-plan` |
| 5 | 旁白后写 | **LLM（写作）或会话内模型** | `narration.json` / `align.json` | 不可跳 |
| 6 | lint 契约 | 纯算法 | 违规清单（阻断=3） | `--no-lint-block` |
| 7 | TTS + 弹性适配 | edge-tts + 算法 | `tts/NNN.mp3` / `qc_report.json` | `--skip-tts` |
| 8 | 混音 → 合片 | ffmpeg（门禁在两处） | `out/03-rapid-narration.mp4` | `--skip-render` |
| 9 | 逐句质检 | **LLM（视觉）** + 算法合并 | `qc_visual.json` / `qc_rewrite.json` | 不加 `--qc` 就不跑 |

注意第 4 步在第 5 步**之前**：画面先切出来，旁白才有东西可对着写。这是整条链的核心时序。

## 一、剧情理解怎么实现

### 1. 台词源先于一切
- 有内嵌 ASS/SRT 就直接提取（`subs_extract`），没有才跑 faster-whisper。
- 译中来自 `cache/asr/<pkey>/asr_zh.json`，按 `paras[i]` 索引套用，缺失回退日文原文。
- 依据：`aicutplan/shared/story_parse.py:183-202`、`aicutplan/shared/asr_pipeline.py:49-93`。

### 2. 事件：按 180s 分段，多模态一次调用
- 每段喂「该段全部台词（源片秒）+ 12 张均匀抽帧」，要求产出 8–14 个**连续**事件，
  `t0/t1` 必须落在段内、首尾相接；`type` 是六标签之一；`keep` 是建议保留秒数（2–12）。
- 片头/标题卡 `type=收录`、`keep=0`，直接不进正片。
- 缓存：`cache/story/<md5(工程路径)[:12]>/seg_NN.json`，键是
  `content_sig("segv2", 段区间, 抽帧, 模型, 台词全文, shots_desc 指纹, scene_desc 指纹)`。
- 依据：`story_parse.py:44-57`（`SEG_Q` 的 schema 与规则）、`:324-361`（主流程）、`:294-321`（指纹）。

**这意味着**：剧情理解的「分辨率」是 180s 一段、8–14 个事件。它不是逐帧理解，而是
「这段里发生了什么、按顺序」；画面细节靠 `shots_desc`（读图产出的镜头描述）补。

### 3. 块：把事件压成六段式叙事
- 一次调用喂「全部事件一行一条 + 目标时长 + 刀数 + 字数预算 + 六段式模板」，
  要 12–15 块、首块必须是钩子、Σtarget 落在目标时长 95%–104%、单块 8–30s。
- 块字段：`label / type / t0 / t1 / target / summary`——**带源片区间**，这是后面选镜的锚。
- 依据：`story_parse.py:62-82`（`BLK_Q`）、`:527-585`（规范化、字数预算、总长归一）。

### 4. 因果图谱（增强项，可跳过）
- 给非收录事件逐条补 `func / cause / result`，`func` 限六个标签（铺垫/升级/爆发/爽点/钩子/收束）。
- 证据回喂：每个事件取 `score_shot` 最高 2 个镜头的 `desc[:22] + dlg[:18]`，
  并在 prompt 末尾声明「截图只覆盖少数时刻，以证据包为准」。**喂的是镜头文字，不读图。**
- 产物写 `json/story_plan.json` 的 `causal` 字段；已有缓存默认复用，`--force` 才重调。
- 依据：`causal_graph.py:33-48`、`:52-91`、`evidence_feed.py:45-77`、`evidence.py:35-64`。

### 5. 钩子：先锁一段「连续未裁切」的爽点
- 打分：`关键词A(+2.0) + 关键词B(+3.0) + type=爽点(+1.5) − 镜长>6s(2.0)`；
  在镜头序列上滑一个预算长的窗，按 `Σ(权重×重叠秒)/预算` 取最高。
- 连续性：相邻窗 `src_start − 上一窗 src_end ≤ 0.05s`。
- 实践中 `recap.hook_clip` **由导演稿的 `hook` 写死**（人工/会话决定），cutfirst 只当 override；
  契约还会校验它与钩子窗的区间差（≤0.6s 起 / ≤1.0s 止）与「专属句 ≥2」。
- 依据：`planning.py:40-52`、`:55-93`、`:118-125`；`cutfirst_plan.py:134-150`；`contracts.py:331-354`。

### 6. 选窗：块预算 → 事件权重 → 领镜
- 每块把 `target` 按事件权重分配：`func` 权重 3.0/2.6/1.8/1.3/1.0，有因果连接 ×1.15；
  爆发保底 5s、其余 1.6s；超额按 `max(0.4, 1−over/Σ)` 回缩。
- 每个事件按时间领「未用过的整镜」，窗口时长 `clamp(镜长, 0.8, 3.5)`，<0.45s 碎镜跳过，
  不够就向 ±1/±2 相邻事件借。
- `tier` 默认 `line`；块内「爆发」到「收束」前（4–15s）标 `hold_hl/original`（原声留白），
  末块尾部约 12s 同样留白。
- 依据：`cutfirst_plan.py:69-80`、`:123-163`、`:165-220`、`planning.py:96-104`。

## 二、文案怎么写

### 路径 A：会话内导演（主线，零 API）

`narrate --export` 生成 `window_table.md`，**按块分组**，一行一个窗口：

```
## 块1 前情（铺垫）
窗口11 | 成片 15.5-19.0s (3.50s, 预算≈16字) | 画面: 紫光笼罩少年→黑发少年紫光中回头微笑→石墙前正面自信笑 |
台词: … | 深层: 强化完成后的自信亮相，主角确立 | 帧事实: 50s:紫光裹身 / 53s:回头微笑 | 关键词: 雷恩,紫光,微笑
```

- 列：`窗口号 | 成片秒(时长,预算≈N字) | 画面 | 台词 | 深层 | 帧事实 | 关键词`。
- 钩子块只列槽位、不给画面证据（因为正片原样复用，不参与写作）。
- 留白窗写 `【原声留白·不写句】画面自己演：…`。
- 依据：`narration-chain` 报告对应 `narrate_cut.py:132-163`、`:96-103`。

模型逐行读表（43KB，建议按块分批 `read`），对着「画面 + 台词 + 深层」写 `sents.json`：

```json
[{ "ws": 0, "we": 1, "text": "他有个神技，万物皆能强化", "src": [809.67, 812.1] }]
```

`src` 必须是**首窗 src_start → 末窗 src_end**；`i/t0/dur` 由 narrate 现算，不写进稿子。

### 路径 B：LLM 自主写作（有 key 时）

`narrate_cut` 内部走 DeepSeek，prompt 里给三条硬约束：字数 `rate×0.95±1`、句长上限、
禁止总结陈词。5 套模板在 `config/templates.json`（六段式梳理 / 整稿 / 单块改写 / 润色 ≤14 字 / 审稿），
web 旁白台可改。依据：`templates.json`、`narrate_cut.py:53`、`:272`。

### 字数预算公式

```
预算 ≈ 窗口组总时长(s) × 4.95(字/秒) × 0.95 ≈ 时长 × 4.7
```

- 1.2s 一窗 ≈ 5 字；3.5s 一窗 ≈ 16 字；一句最多跨 6 窗。
- 表里的 `预算≈N字` 是**写死 `int(dur*4.7)`**；`--rate` 只改提示词与表头文字，
  不改表内预算——这是当前的口径隐患，改语速标定时要留意。
- 依据：`narrate_cut.py:103`、`:162`、`:53`。

### 导演稿（批量出片用）

`batch/planner.py` 的导演稿是**数据**：`title / hook[a,b] / hook_lines(≥2 句) / tail[a,b] / span(11.5) / chunks[[a,b,[句子…],类型]]`；
`chunks` 第三项为空即原声段。planner 生成 cutplan / meta / story_plan / sents，并回写 `recap.hook_clip`。
依据：`planner.py:22-32`、`:58-78`、`:166-171`、`:213-220`。

## 三、文案和画面怎么对齐（五道锁）

| 锁 | 机制 | 失败表现 |
|---|---|---|
| ① `src` 绑定 | 每句声明源片区间，必须等于绑定窗口的 `src_start/src_end`（容差 0.6s/1.0s） | 退出码 **5**，不写任何产物 |
| ② `t0` 锁定 | `t0 = windows[ws].new_start`，容差 **1ms** | `check_alignment` 报错；画面与语音整体偏移 |
| ③ 规则 lint | 未覆盖窗、超槽、顺序回跳、重复覆盖、钩子契约 | cf_pipeline 阻断，退出码 **3** |
| ④ TTS 弹性适配 | 槽位 = 尾窗 end − 首窗 start **+0.15s**；`ratio = 实测语音/槽位` | `ratio>1.35` 标 `OVER`，只报告不裁剪 |
| ⑤ 质检闭环 | 抽帧取**句首窗中点**（`wins[lo].new_start + min(窗长,1.2)/2`），判定→改写→只重合成改动句 | mp3 mtime 未更新即中止（防「新词旧音频」） |

### 为什么「一句跨多窗」不会音画错位
因为 `t0` 和 `dur` 来自**窗口组**（首窗 start、尾窗 end），不是来自 TTS 时长；
TTS 的实测时长被 `elastic_fit` 压进 slot（≤1.15 用 atempo；1.15–1.35 用 +55% 语速重合成），
画面刀点完全不动。语音偏短不补静音、不拉伸，留白就当呼吸。

### 为什么「重切之后必须重跑 narrate」
`cut.py` 会把帧网格吸附后的精确时间回写 `cutplan.json`，整体可能偏 ~0.04s；
`check_alignment` 容差只有 1ms，旧 `t0` 必偏，质检抽帧也按 `sent_win_idx` 定位会一起错。

### 质检的时间点为什么取「句首窗中点」
一句可能跨 6 窗，取整句中点会落到后半段画面，判出来的「配不配」是错的；
取首窗中点才对应这句话开始描述的那个动作。暗帧（亮度<16）在同窗 +0.35s 重抽，最多 3 次。

## 四、在 dsh-aicut 里怎么串起来

```
aicut_subs            → ①台词源（有内嵌字幕就不跑 ASR）
aicut_plan            → ②③④ 事件/块/窗口（零 API 时先 --export-prompt 再 --import，插件 P3 补）
aicut_narrate export  → ⑤ window_table.md
（模型 read 表 + 写 sents.json）
aicut_narrate sentences → ⑥ narration.json + align.json（契约不过退出 5）
aicut_check           → ③ lint + ② 对齐 + TTS 一致性
aicut_render          → ④ TTS 适配 + 混音 + 合片
aicut_qc plan/merge   → ⑤ 抽帧判定 → qc_rewrite → 只重合成改动句
aicut_runs snapshot   → 归档 + 指纹校验
```

**一句话**：插件不写一个字、不判一帧；它保证每一步的输入输出是**同一批数据**，
并把「不一致」变成可执行的退出码。

## 四之二、抽帧频率与读图路径（最容易被误解的一段）

**不是「按固定帧率抽视频给 LLM 看」，而是按三种结构单元各抽代表帧，频率差一个数量级。**

| 用途 | 抽帧位置 | 频率 | 分辨率 | 谁读 | 产物 |
|---|---|---|---|---|---|
| 剧情事件 | 每个 180s 段取 12 帧，每格**中点** `t = a + span×(k+0.5)/12` | **1 帧 / 15s** | 宽 320 | 多模态 LLM（12 图 + 该段全部台词，一次调用） | `story_plan.events` |
| 镜头描述 | ≤6s 的镜抽中点 1 帧；>6s 抽 前/中/尾 3 帧（F=a+min(0.5,10%)、L=b−0.5） | **1–3 帧/镜**（漫剪镜长中位 ~1.3–2s，折合每 1–2s 一帧） | 宽 240 | LLM 或会话内分批 `read_image` | `shots_desc.json` |
| 2s 窗场景 | `fps=1/2` 一次抽完全片 | **1 帧 / 2s** | 宽 240 | 旧实现；现由镜头描述推导（零读图） | `scene_desc.json` |
| 逐句质检 | **句首窗中点** `wins[lo].new_start + min(窗长,1.2)/2` | **1 帧/句**（≈ 每 5–6s 成片一帧） | 原比例 | 模型读 2×3 宫格（6 句/张） | `grid_XX.jpg` |
| 镜头切分 | 不抽帧，`ffmpeg select='gt(scene,0.30)'` | 内容自适应（平均 1.5–3s 一刀） | — | 算法 | `shotlist.csv` |

代码依据：`story_parse.py:167`（180s 分段）、`:221-233`（12 帧中点抽样、宽 320）、
`:248-263`（12 图 + 文本一次多模态请求）、`shot_desc.py:52-71`（每镜 1 或 3 帧、宽 240）、
`scene_desc.py:49-59`（fps=1/win）、`qc_visual.py:62-68`（句首窗中点）、
`legacy/shots_scan.py:47`（scene 阈值 0.30）。

**为什么频率差这么多**：段级只需要「这一段发生了什么、按顺序」，12 张足够定 8–14 个事件；
镜像级需要「这个镜头是什么画面」，1–3 张；句级只需要一个「配不配」的判断，1 张。

**三个直接后果**（都是已知限制的成因）：

1. 320px 宽只够认人、动作、颜色，**读不清画面里的小字**——「十三万点 → 一万三千点」这类
   数字事实错误就出在这里，目前靠人工发现。
2. 1 帧/15s 会**漏掉快动作**（0.5s 的挥剑可能一张都没拍到），所以事件里「发生了什么」
   主要来自台词，画面只补场景/表情/姿态。
3. 帧是**按文件名缓存复用**的（`s{段号}_{秒}.jpg`，存在且 >800 字节就跳过重抽），
   换源片不会自动失效，必须清 `frames/` 目录。

## 五、当前薄弱点（别当成已解决）

1. **剧情理解的质量上限由 `shots_desc` 决定**。不读图就只有台词，事件会退化成「谁说了什么」，
   画面里的动作/表情/字幕数字全靠抽帧那 12 张。
2. **因果图谱默认要 key**；零 API 只能导出 prompt 让会话里的模型补，再 `--import` 回来。
3. **预算与 `--rate` 脱钩**（写死 4.7），改语速标定后表内预算不跟着变。
4. **`OVER` 只报告不处理**：超槽 35% 以上的句子会溢出槽位，需要人改词。
5. **71% 覆盖不是目标**：EP01 语音覆盖 84.9%、原声留白 31%，留白是设计（爽点让原声演），
   不要为了「覆盖率」去填留白窗。
